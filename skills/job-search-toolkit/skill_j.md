# Job Search Toolkit (日本語版)

## スキルの範囲と限界（はじめにお読みください）

- 本スキルのスコアリングは、**正確な表層表現の一致（exact surface expression overlap）**を測定するように設計された決定論的スクリプト（`scripts/score_posting.py`）に依拠しています。
  - **英語/ラテン文字テキスト**: 単語境界（`\b[A-Za-z][A-Za-z0-9+#./-]*\b`）、ASCII小文字正規化、基本ストップワード（Stopwords）除去、未認識の大文字略語（2〜6文字）の抽出を行います。
  - **日本語/韓国語テキスト**: 空白および句読点・記号（`、`、`。`、`「`、`」`、`【`、`】`、`・`など）で区切られた表層チャンクをキーワードとして抽出します。**形態素解析器は使用していません。** したがって、「Pythonの」「APIでの」「クラウドに」のように助詞が結合した表層チャンク単位で処理されるため、ノイズが含まれる場合があります。
  - **レキシコン（`--lexicon`）**: 複数の語からなる複合技術用語（例: `machine learning`、`機械学習`、`マイクロサービス`、`スクラム開発`、`要件定義`、`React Native`、`CI/CDパイプライン`）は、レキシコンファイルに登録することで、文書全体から完全な1つの単位として部分一致マッチングされ、分割や助詞結合による誤認識を防ぐことができます。
- スクリプトが測定するのは、**「両方の文書に同一の表層表現が登場しているか」**のみです。
  求人票の「cross-functional collaboration」と経歴書の「他部門・複数チームとの横断的連携」「worked with other teams」のように、**異なる言い回しで表現された同一要件を、意味的に同一であると勝手に推論することはありません。**
  意味的推論は非決定的（非再現的）であり、モデルの解釈揺れが生じて客観的な監査（Audit）が不可能になるためです。
  したがって、スクリプトが算出したギャップ（Gap）は「表現上のギャップ」として解釈し、実際のスキル・経験の有無は人間が確認した上で最終アクションを決定します。
- **カバレッジの単一数値のみで合否や適性を判定してはなりません。**
  全体のカバレッジ率（%）は、ギャップ一覧、制約条件（給与・勤務形態・経験年数）、未認識の求人表現、そして**カテゴリ別カバレッジ（必須要件 required / 歓迎要件 preferred / 指定なし unmarked）**と必ずセットで立体的に読み取ります。
  全体カバー率が80%と高くても必須要件（required）が欠落していれば書類選考落ちのリスクが高く、逆にカバー率が40%でも必須要件をすべて満たしており未達項目が歓迎要件（preferred）のみであれば、十分に挑戦可能なポジションと判断できます。
- **必須/歓迎の分類は近傍ヒューリスティック（Proximity Heuristic）で行われます。**
  求人票テキスト内の必須マーカー（`required`, `must`, `必須`, `必須要件`, `必須条件`, `求めるスキル`等）または歓迎マーカー（`preferred`, `nice to have`, `歓迎`, `歓迎要件`, `尚可`, `優遇`等）の前後250文字以内に登場したキーワードを該当バケットに分類します。求人票がセクションで明示的に必須・歓迎を分けている場合は、求人票原文の区分を最優先とし、スクリプトの分類は補助指標として参照します。

## なぜこのスキルが必要なのか

一見もっともらしいマッチングスコアを出すツールは、本当に機能しているツールと見分けがつきません。
その違いは、実際の採用選考の現場で検証されたときに初めて明らかになります。

初期の単純なLLMプロンプトによるワークフローでは、クロワッサン生地の折り込み成型、早朝5時出勤、「パソコン業務なし」と明記されたパティシエ（製菓職人）の求人票に対し、一般的なITエンジニアの職務経歴書を入力した際に「適合度92%」と高評価を下す致命的な欠陥が発生しました。モデルが具体的な検証可能条件を確認せず、表面的な雰囲気だけでパターンマッチングを行ったためです。

本スキルは、このような致命的なミスを根本から排除するために設計されています：
1. 計算可能な決定論的数値は、スクリプトコードによって厳格に計算する。
2. 求人票に明記されていない制約事項は推測せず、`NOT STATED`（記載なし）として報告する。
3. 元の職務経歴書に存在しない架空の実績、経験年数、スキルを創作（ハルシネーション）しない。

## 4つのコアコマンド

ユーザーが希望する支援内容に応じて、必要なワークフローを的確に実行します（通常は1つずつ段階的に進めます）。

1. **求人票スコア算出 (Score)** — 職務経歴書と求人票の間でキーワード網羅率（全体および必須/歓迎別）とギャップを算出します。
2. **職務経歴書の最適化 (Tailor CV)** — 候補者が実際に持つ実務経験を、応募先求人票の優先順位に合わせて構成・表現を最適化します。
3. **志望動機・自己PR草案作成 (Cover Letter / Motivation)** — 両文書で合致している中核的な強みを根拠に、説得力のある志望動機・自己PRを執筆します。
4. **面接対策パック作成 (Interview Prep)** — 求人要件と職務経歴書のギャップから、面接官が突いてくる想定質問と回答ロジック・逆質問を設計します。

## 厳格な事実根拠ルール（Fact-Grounding Rules - 全コマンド共通）

このルールはスタイルの提案ではなく、スキルの信頼性を担保する絶対厳守の制約です：

1. **表現の洗練・再構成は推奨するが、虚偽の創作は一切禁止する。**
   - 「社内ツールの開発を行いました」を求人票のトーンに合わせて「業務効率化のための社内管理ツール・ダッシュボードの設計・開発」と具体化することは推奨されます。
   - しかし、職務経歴書に存在しない技術スタック、架空の数値、資格、実務年数を勝手に追加することは固く禁じます。
2. **スクリプトが解釈できない求人票表現は、スコアから黙って削らずユーザーに明示する。**
   - 辞書やレキシコンにない社内ツール名や特殊な略語は、`unrecognized_posting_language`としてリスト化し、ユーザーに確認を求めます。
3. **記載のない制約条件は「NOT STATED」として報告し、決して推測しない。**
   - 給与レンジ、勤務形態（リモート/出社）、必須経験年数が求人票に記載されていない場合、業界の相場などを勝手に推測せず`NOT STATED`と報告し、面接時の逆質問候補として整理します。
4. **主観的な合否判定や大げさな評価を下さない。**
   - 「合格確実」「強く推薦」「完全なマッチ」のような主観的判定は行いません。カバレッジ率は文書間のテキスト一致指標に過ぎず、採用の意思決定は人間側が行うものとします。
5. **文脈による同音異義語・技術用語の混同に注意する。**
   - 「ハイブリッド検索」「ハイブリッドクラウド」のような技術用語を「ハイブリッド勤務（リモート＋出社）」と誤判定しないよう、スクリプトの除外ガードと原文文脈を確認します。
6. **対話の中で新たに判明した事実の明示的タグ付け:**
   - ユーザーが対話の中で「実はその案件でX技術も使っていた」「資格を持っているが経歴書に書き忘れていた」と新事実を述べた場合、それを原稿に反映することは可能です。
   - ただし、その記述の直後には必ず `[新規確認: 対話内で直接言及]` というタグを付与します。
   - 例: `リアルタイム異常検知パイプラインの設計およびKafka連携 [新規確認: 対話内で直接言及]`
   - ユーザーが最終確認して承認するまでは、草案・成果物からこのタグを勝手に削除してはなりません。

## CLI実行およびJSON連携ガイド

`scripts/score_posting.py` は外部ライブラリ依存がなく、Python 3の標準ライブラリのみで動作します。

### 実行コマンド例

```bash
# 1. 通常のテキストレポート出力
python scripts/score_posting.py resume.txt posting.txt

# 2. 複合用語レキシコンファイルを指定して実行
python scripts/score_posting.py resume.txt posting.txt --lexicon lexicon.txt

# 3. JSONフォーマット出力（エージェント自動連携・詳細解析用）
python scripts/score_posting.py resume.txt posting.txt --lexicon lexicon.txt --json
```

### レキシコン（`lexicon.txt`）の作成指針
- 1行に1つの複合技術名や固有名詞を記載します（`#`で始まる行はコメント）。
- 例:
  ```text
  # 主要技術スタック
  machine learning
  機械学習
  マイクロサービス
  スクラム開発
  Kubernetes
  React Native
  PostgreSQL
  要件定義
  基本設計
  ```

### JSON出力スキーマ概要
```json
{
  "overall_coverage_pct": 68.4,
  "overall_matched": 13,
  "overall_total": 19,
  "category_coverage": {
    "required": { "matched": 7, "total": 8, "pct": 87.5 },
    "preferred": { "matched": 4, "total": 7, "pct": 57.1 },
    "unmarked": { "matched": 2, "total": 4, "pct": 50.0 }
  },
  "matched_terms": ["docker", "python", "sql"],
  "gap_terms": ["graphql", "kafka"],
  "gap_terms_by_category": {
    "required": ["kafka"],
    "preferred": ["graphql"],
    "unmarked": []
  },
  "constraints": {
    "salary": "年収800万円〜1200万円",
    "work_arrangement": "remote (matched \"在宅\", context: \"...\")",
    "years_experience": "3年以上"
  },
  "unrecognized_posting_language": ["APM", "GRPC"]
}
```

## ステップ別ガイド: 求人票スコア算出 (Command 1)

1. **入力テキストの言語と状態確認**:
   - 専門用語や複合名詞が多い場合は、レキシコン（`lexicon.txt`）の併用を検討します。
2. **スクリプトの実行**:
   - `python scripts/score_posting.py resume.txt posting.txt [--lexicon lexicon.txt] [--json]`
3. **スコアレポートの標準提示形式**:
   - **全体カバレッジ**: 一致数 / 全要件数 および一致率（%）
   - **カテゴリ別カバレッジ**:
     - 必須要件（Required）: X/Y (Z%) — *最も重視すべき選考基準*
     - 歓迎要件（Preferred）: X/Y (Z%) — *差別化・加点要素*
     - 指定なし（Unmarked）: X/Y (Z%)
   - **制約条件（Constraints）**: 年収レンジ、勤務形態、要求実務年数（未記載はNOT STATED）
   - **一致した主要キーワード**: 双方の文書に明記されているスキル・経験
   - **カテゴリ別ギャップ（Gap）一覧**:
     - 必須要件のギャップ（Hard Gap）: 書類選考や面接で重点的に釈明・フォローが必要な項目
     - 歓迎要件のギャップ（Soft Gap）: 必須ではないが留意すべき項目
   - **未認識の求人表現**: 確認を要する略語や社内用語
4. **分析・解説コメントの提供**:
   - 表層上のギャップと実際の経験の乖離の有無（例: 求人票の「スクラム開発」と経歴書の「アジャイル型スプリント運用」）
   - 日本語の助詞結合ノイズの有無の整理
   - 致命的な選考リスクの有無（必須ギャップの重要度判断）

## ステップ別ガイド: 職務経歴書の最適化 (Command 2)

1. **マッチング結果の活用**:
   - スコアリングで得られた `matched_terms` と `gap_terms_by_category` を出発点とします。
2. **合致項目のアピール度向上**:
   - 経歴書内に埋もれている実際の関連経験を、求人票の用語に合わせて自然に目立たせます。
   - 職務要約（サマリー）や各社での職務内容の箇条書き上位に配置し直します。
3. **ギャップ項目の誠実な取り扱い**:
   - 未経験のスキルを捏造して埋めることは絶対に行いません。
   - 対話の中でユーザーから直接確認が得られた新事実のみ、`[新規確認: 対話内で直接言及]` タグを付けて追記します。
   - 完全に未経験の必須要件は、経歴書で無理に繕わず、志望動機や面接で近接スキルの応用力として説明する戦略をとります。
4. **提出フォーマット**:
   - **最適化後の職務経歴書全文**
   - **変更内容の比較要約表（Diff Table）**:
     | 箇所 / 職歴 | 変更前の表現 | 最適化後の表現 | 変更理由・求人要件との関連 | 出典 |
     | :--- | :--- | :--- | :--- | :--- |
     | 〇〇社 / 開発実績 | バックエンド開発を担当 | 大規模トラフィック下でのGo/PythonによるAPI設計・性能改善 | 求人票の必須要件と合致させ具体化 | 経歴書原文 |
     | 保有スキル一覧 | Python, MySQL | Python, MySQL, Kafka連携データパイプライン | 必須要件の経験を反映 | 新規確認（対話） |

## ステップ別ガイド: 志望動機・自己PR草案作成 (Command 3)

1. **強みのアンカー（Anchor）選定**:
   - 抽象的で一般的な熱意表明を避け、スコア算出で確認された**確実に裏付けのある中核強み・実績の中から、最も求人に適合する2〜3点**を軸に据えます。
2. **要件ギャップへの誠実で戦略的なアプローチ**:
   - 求人票が求めるが経歴書で不足している領域を、嘘でごまかさないようにします。
   - 近接する技術経験（例: Kafkaの業務経験はないが、RabbitMQによる非同期メッセージングの大規模運用実績がある等）を根拠として、キャッチアップ力と親和性を論理的かつ誠実に記述します。
3. **構成案**:
   - **導入（志望理由の要約）**: 応募先企業のビジョン・事業課題への共感と、自身の専門性が貢献できる領域の要約。
   - **本論1（中核強みの実績証明）**: 1つ目のアンカーについて、具体的な課題状況、取った行動、定量・定性の成果。
   - **本論2（組織・協調・応用力）**: 2つ目のアンカーの証明と、応募ポジションの期待役割との直接的な接続。
   - **本論3（課題認識とギャップ克服）**: 不足要件に対する率直な認識と、近接知見を活かした自律的学習・貢献計画。
   - **結び**: 入社後の具体的な貢献ビジョン。

## ステップ別ガイド: 面接対策パック作成 (Command 4)

1. **ギャップに基づく想定圧迫質問への防御（Gap Defense）**:
   - 面接官が最も深く追求してくるのは、**求人票の必須要件（required）のうち経歴書に記載のないギャップ**です。
   - 各ギャップについて予想される質問を挙げ、STAR法（Situation - Task - Action - Result）に基づいた誠実で現実的な回答骨子を作成します。
   - 知らないことを知っているように装うのではなく、「現状の理解度＋近接スキルの実績＋即戦力化に向けた学習プラン」を堂々と説明できるスクリプトを提供します。
2. **中核強みに関する深掘り質問への対策**:
   - 合致している主要スキルについて、技術的な深さ、トレードオフの判断理由、失敗からの学びを問う深掘り質問を想定します。
3. **未記載制約に基づく戦略的逆質問リスト（Reverse Questions）**:
   - 求人票で `"NOT STATED"` と判定された項目（実際のチーム体制、オンコール頻度、デプロイサイクル、技術的負債への向き合い方、入社後3ヶ月で期待される具体的成果など）を、候補者側から面接官に投げかける洗練されたプロフェッショナルな逆質問としてまとめます。
