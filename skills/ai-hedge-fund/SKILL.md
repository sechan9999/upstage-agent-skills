  파이프라인의 설계 청사진을 만드는 스킬이며, 실거래·실자본 운용에는 쓰지 않는다.

# Skill: AI Hedge Fund (모듈형 에이전트 헤지펀드 설계)

> AI로 운용되는 헤지펀드를 모듈 단위 에이전트로 만들어 서로 연결하고, AQR 스타일의
> 팩터 기반 운용 + 리스크 중립화 + 성과 귀인 구조를 복제하는 **설계 스킬**이다.
> 실제 매매를 실행하는 스킬이 아니라, 데이터·리서치·운용·리스크·엔지니어링을 맡는
> 에이전트들을 어떻게 나누고 연결할지 정리해 주는 청사진을 만든다.

**전제 환경 예시:** (예: 타임리 Agent × Solar Pro 4 같은 조합) — 이 스킬은 특정 에이전트
프레임워크나 LLM을 전제하지 않는다. 실제 구현 범위는 사용자가 실제로 쓰는 에이전트·LLM·코드
조합에 따라 달라지므로, 위 예시는 "이런 식의 조합을 쓸 수 있다"는 참고일 뿐 요구사항이 아니다.
이 스킬은 "한 번에 완성되는 펀드"를 약속하지 않는다 — **작은 모듈을 먼저
만들고 연결을 점진적으로 확장하는 설계**로 접근한다.

---

## 이 스킬이 트리거되면 가장 먼저 할 일

한 번에 조직 전체를 설계하려 들지 말고, 아래 순서로 범위를 좁혀가며 진행한다.

### 1단계 — 범위를 먼저 확인한다 (Phase 0 체크리스트)

아래 4가지를 확인하기 전에는 조직도부터 그리지 않는다. 확인 없이 전체 조직을 한 번에 설계하면
실제로 구현 가능한 범위와 무관한 청사진이 나오기 쉽다. 확인은 대화에서 바로 체크할 수 있게
짧은 질문 형태로 처리한다.

- **데이터 접근성**: 실제로 어떤 데이터를 어떤 형식으로 확보 가능한가 (아래 "필요 데이터"의
  Tier 1/2/3 참고). 전부 없어도 되지만, **현재 확보된 것과 아직 없는 것을 분리**해 적는다.
- **계산 자원과 비용 한도**: 백테스트 한 번, 팩터 계산 한 번, 데이터 정합 점검 한 번에
  어느 정도 시간·계산량·토큰/비용을 써도 되는가. "무제한"이 아니라 **실제 상한**을 정한다.
- **자동화 vs 승인 경계**: 어떤 결정까지 자동 실행을 허용하고, 어떤 결정은 사람 승인이 필요한가.
  예: 팩터 계산·데이터 정합은 자동 가능, 전략 채택·운용 규칙 변경·노출 한도 변경은 승인 필요 등
  (아래 오케스트레이션의 G0~G3 게이트와 짝지어 정한다). 특히 "되돌리기 어려운 행동"은 승인
  게이트로 남긴다.
- **시작 모듈**: 전체 조직 중 진짜 먼저 만들 것은 무엇인가. 보통 하나만 고른다.
  예: 데이터 검증 + 팩터 계산 + 단순 백테스트 + 리스크 중립화 중 한두 개.

위 4가지가 정리되면, 그 범위 안에서만 2단계 오케스트레이션 골격을 맞춘다. 4가지가 비어 있으면
조직도는 "그럴듯하지만 구현되지 않는 청사진"이 되기 쉽다. 데이터·예산·승인 정책이 바뀌면
이 체크리스트도 다시 확인한다 — 1회성 킥오프 절차가 아니라 범위가 바뀔 때마다 되돌아오는 게이트다.

### 2단계 — 아래 오케스트레이션 순서를 기본 골격으로 제안한다
에이전트들을 병렬로 늘어놓지 말고, **의존성 + 승인 게이트 + 데이터 흐름 + 피드백 루프**를 중심으로 연결한다.
직선 파이프라인이 아니라, 각 단계는 다음 단계로만 진행하지 않고 이전 단계로 되돌아갈 수 있는
**되돌림 경로(reject/return path)**를 함께 갖는다.

1. **CTO/engineer**가 데이터를 수집·검증해 리서치 가능한 상태로 만든다.
   - 데이터 이슈 발견 시 하류 전체를 멈추고 엔지니어링으로 되돌아간다 (승인 게이트 G0).
2. **주니어 리서치**가 아이디어를 생성하고 초기 검증을 수행한다.
3. **시니어 리서치**가 백테스트와 이론적 타당성을 검토해 채택/기각한다 — 기각 사유도 반드시 기록한다 (승인 게이트 G1).
   - 기각된 아이디어는 사유와 함께 주니어 리서치로 되돌려 재작업 여부를 판단한다.
4. 채택된 전략을 **quant pm / 차익거래 pm / 매크로 pm**이 실제 운용 규칙으로 변환한다.
5. **CRO/risk model**이 리스크 중립화와 노출 제한을 적용해 PM에게 되돌려준다 (승인 게이트 G2).
   - 리스크 예산 초과 시 PM에게 반려하고, PM은 포지션/전략 조합을 조정해 재제출한다.
   - G2는 두 층위로 나눠서 본다: ① **PM별 개별 승인** — quant/차익거래/매크로 PM 각자의 전략이
     자기 리스크 예산 안에 있는지, ② **firm-wide 합산 점검** — 3개 PM 북(book)을 CRO가 하나로
     합쳐 섹터·팩터·통화 노출이 중복되지 않는지 확인. PM별 승인만 통과하고 firm-wide 합산을
     생략하면, 개별로는 문제없어 보이는 포지션들이 합쳐졌을 때 의도치 않게 노출이 커질 수 있다
     (예: quant PM의 금리 민감 팩터 롱 + 매크로 PM의 금리 매크로 롱이 겹치는 경우). firm-wide
     합산은 마지막 PM이 제출을 마친 뒤, G3(CIO 최종 승인) 이전에 한 번 더 수행한다.
6. 실제/모의 운용 후 **attribution**과 성과 점검으로 다시 피드백한다.
   - attribution 결과는 두 갈래로 되돌아간다: 신호 열화가 원인이면 시니어 리서치로, 리스크
     노출 문제면 CRO로 피드백해 원인 계층에서 바로잡는다.
7. **CIO**가 전체 우선순위, 자원 배분, 승인/보류/종료를 결정한다 (승인 게이트 G3, 최종 게이트).
   - CIO 판단은 다시 1단계 범위 재확인이나 특정 모듈의 우선순위 재배치로 이어질 수 있다 —
     오케스트레이션은 열린 루프이지 1회성 파이프라인이 아니다.

승인 게이트 요약 (자동 진행 vs 사람 승인 필요는 1단계에서 정한 정책을 따른다):
- **G0 (데이터 품질)**: 엔지니어링 검증 통과 전에는 리서치 착수 금지
- **G1 (전략 채택)**: 시니어 리서치의 채택/기각 없이 PM 단계로 넘어가지 않음
- **G2 (리스크 승인)**: CRO의 PM별 개별 승인 + firm-wide 합산 노출 점검 없이 라이브/페이퍼 운용으로 전환하지 않음
- **G3 (CIO 최종 승인)**: 자본 배분·자동화 범위 확대·전략 종료는 CIO 승인이 최종

이 흐름에서 놓치기 쉬운 점:
- 백테스트는 데이터 누수, survivorship bias, 전후처리 일관성, 거래비용 반영 여부를 반드시 점검한다.
- 운용과 리스크는 분리해서 설계하되, 실제로는 리스크 예산이 전략 선택을 제한하도록 연결한다.
- 매크로·차익거래는 독립 전략처럼 보여도, 전체 포트폴리오 관점에서 노출 중복을 점검해야 한다.
- 되돌림 경로 없이 앞으로만 진행하는 파이프라인으로 그리면, 실패한 전략이 왜 실패했는지
  원인 계층(데이터/리서치/리스크)까지 피드백되지 않고 같은 실수가 반복된다.

### 3단계 — 범위에 맞는 모듈만 구체화한다
전체 조직도를 다 채우려 하지 말고, 1단계에서 확인한 범위(데이터·예산·승인 정책·시작 모듈)에
맞는 역할만 골라 아래 "조직 구조와 역할"에서 구체화한다.

## 핵심 목표 / 레이어

- 데이터를 모으고 검증하는 **엔지니어링 레이어**
- 팩터·포트폴리오·거래비용·대체투자 신호를 연구하는 **리서치 레이어**
- 연구 결과를 백테스트하고 이론/성과 기준으로 채택·기각하는 **시니어 검토 레이어**
- 포트폴리오를 만들고 리스크를 중립화하는 **운용 레이어**
- 매크로·차익거래로 전략을 보완하는 **멀티에셋/아비트라지 레이어**
- 리스크 모델(Barra 계열)과 성과 분해를 담당하는 **리스크 레이어**
- 전체를 조율하는 **오케스트레이션 + 토큰 결제/운영 흐름**

## 조직 구조와 역할

### CIO: 투자본부
전체적으로 무엇을 연구·채택·운용할지 결정하고, 전략과 리스크의 균형을 관리한다.
- 어떤 팩터/전략/매크로/차익거래를 개발 파이프라인에 넣을지 우선순위 결정
- 백테스트 결과만이 아니라 경제적 논리·회전율·거래비용·리스크 노출까지 종합 판단
- 운용 규모에 따른 실행 가능성, 용량(capacity), 유동성 제약을 고려
- 신용·레버리지·숏 제한, ESG/규정 준수 등 운용 제약 승인

### 주니어 리서치
아이디어를 만들고 초기 검증을 수행한다.
- **factor research**: 팩터 관련 논문·기존 성과·구현 가능성 연구
- **portfolio research**: 전통 최적화 + ML 기반 포트폴리오 구성 방법 연구
- **execution research**: 거래비용, 슬리피지, 공매도 비용, 실행 알고리즘 연구
- **alternative signal**: LLM 등을 활용해 텍스트·뉴스·이벤트 기반 알파 후보 탐색

주니어 리서치는 "아이디어 제안 + 작은 검증"까지 맡고, 시니어가 채택 여부를 검토하는 구조가 적합하다.

### 시니어 리서치
주니어가 만든 주제를 다방면으로 분석하고 채택/기각을 결정한다.
- **strategy backtest**: 편향 통제, 시점 누수 방지, 비용 반영, 유니버스 변화, 과적합 점검 포함 분석
- **head researcher**: 성과뿐 아니라 경제적 이론, 리스크 노출, 회전율을 종합해 채택/기각
- 재현성·안정성·아웃오브샘플 성능을 중시
- 한 전략의 강점/약점/실패 조건/용량 한계를 문서화

### 퀀트운용팀
팩터 라이브러리를 바탕으로 실제 포트폴리오를 만든다.
- **quant pm**: 팩터 익스포저, 섹터/국가/스타일 제약, 리스크 예산, 회전율, 리밸런싱 주기 등을 반영해 포트폴리오 구성
- 리스크 예산과 투자 아이덴티티를 동시에 만족시키는 방향으로 조정
- 라이브/페이퍼/스케일업 단계별 운용 규칙 정리

### 차익거래팀
차익거래 기회를 연구하고 관련 포트폴리오를 만든다.
- **arbitrage research/pm**: 합병차익, 이벤트차익, 상대가치, 통계차익 등 검토
- 실행 위험, 자금조달, 공매도 제약, 이벤트 실패 리스크, 유동성 위험을 함께 고려
- "이론적 차익"과 "실제 실행 가능 차익"을 구분

### 매크로팀
매크로 데이터를 이용한 멀티에셋 롱/숏을 연구·운용한다.
- **macro research/pm**: 금리, 환율, 물가, 경기, 신용, 원자재 등 다차원 신호 연구
- 자산군 간 상관, 레짐 변화, 정책 이벤트, 유동성 환경 반영
- 롱/숏 방향과 포지션 사이징을 매크로 모델과 리스크 예산 안에 통합

### CRO: 리스크본부
리스크 모델과 성과 분해를 담당한다.
- **risk model**: Barra 스타일의 섹터/팩터 중립화, 리스크 분해, 노출 관리 — quant/차익거래/매크로
  PM별 개별 리스크 예산 점검과, 3개 PM 북을 합산한 firm-wide 노출 점검을 모두 수행한다 (오케스트레이션
  G2 참고). 개별 PM 승인만으로는 팀 간 노출 중복(예: 여러 PM이 같은 방향의 금리 익스포저를 쌓는 경우)을
  잡을 수 없다.
- **attribution**: 운용 레코드 성과를 요인/섹터/selection/allocation 등으로 분해
- 위험 한도, 스트레스 테스트, 꼬리 위험, 레버리지/유동성 리스크 점검

### CTO: 엔지니어링
데이터 수집, 오류 검증, 새로운 데이터 발굴, 파이프라인 안정성을 담당한다.
- **engineer**: 데이터 수집 자동화, 품질 검증, 이상치/단절/수정 데이터 처리, 신규 데이터 소스 발굴
- 데이터 이슈는 투자 판단에 들어가기 전에 먼저 걸러내는 것이 핵심
- 재현 가능한 파이프라인, 버전 관리, 데이터 카탈로그, 감사 추적 확보

## 필요 데이터 (요청된 범위)

데이터는 "다 있어야 시작 가능"이 아니라 **접근 가능한 범위에 따라 티어를 나눠** 시작한다.
1단계에서 확인한 데이터 접근 범위를 아래 티어 중 어디에 해당하는지 먼저 판단한다.

### Tier 1 — 최소 시작 요건 (이것만 있어도 팩터 리서치 착수 가능)
- 전 종목 주가, 수정계수, 거래량, 거래대금, 섹터 정보, 거래소
- 기본 재무제표 (연간/분기, PIT 아니어도 무방 — 단 룩어헤드 리스크는 문서화)

### Tier 2 — 정합성·재현성 강화 (팩터 백테스트를 신뢰 가능한 수준으로 끌어올림)
- 1999년 이후 PIT(point-in-time) 재무제표 — 재무제표 수정/재작성 반영해 룩어헤드 방지
- 기업 이벤트 (배당, 유상증자, 채권발행, 합병, 분할, 상장폐지) — 수정주가·유니버스 정합에 필수
- 2002년 이후 ETF 일별 데이터 — 벤치마크/헤지/유동성 프록시용

### Tier 3 — 확장 모듈 (차익거래·대체투자 신호 등 특정 모듈에서만 필요)
- SPAC 관련 합병/상폐, 예치이율 등 — 차익거래팀 모듈에서만 필요
- 대체 데이터(뉴스/텍스트/이벤트 등 alternative signal 모듈용) — 라이선스·품질 편차 크므로
  단독 신호로 쓰지 말고 보조 신호로 취급 (Guardrails 참고)

Tier 1만 있어도 "데이터 검증 + 팩터 계산 + 단순 백테스트" 모듈은 시작할 수 있다. Tier 2/3는
확보되는 대로 점진적으로 편입한다 — 전 범위를 갖춘 뒤 시작하려 하지 않는다.

### 데이터 처리 레이어
위 데이터는 실무에서 아래처럼 모듈별로 나눠 다루는 것이 좋다. 각 레이어는 이전 레이어의 품질에
의존하므로, 순서를 건너뛰고 상위 레이어(예: feature store)부터 만들면 하류에서 재작업이 발생한다.

- **raw ingestion**: 원본 수집, 형식 통일, 결측/이상치 체크
- **cleaning**: 수정주가/이벤트 반영, 기업 액션 처리, 상장폐지/상폐 후 데이터 처리
- **alignment**: 주가·거래량·재무제표·이벤트의 시점 정합, 생존편의/룩어헤드 방지
- **feature store**: 팩터 계산용 정형 데이터셋, 시점 기준 인덱싱
- **meta data**: 섹터/거래소/유니버스/통화/상장구분 등 식별자 관리
- **data catalog**: 소스별 티어(1/2/3)·최종 갱신 시각·알려진 이슈를 기록해, 리서치 단계에서
  "이 데이터가 어느 정도 신뢰 가능한지"를 매번 재확인하지 않아도 되게 한다

## 토큰 결제 및 운영 흐름

에이전트들이 쉬지 않고 돌아가려면, 작업 단위와 결제 단위를 함께 설계해야 한다.

- 작업 단위를 명확하게 나눈다: 데이터 수집, 팩터 계산, 백테스트, 문서화, 검토, 승인, 리밸런싱, 리스크 점검 등
- 각 작업의 예상 비용/토큰 사용량/우선순위/재시도 정책을 정한다
- 중요한 작업과 반복 작업의 우선순위를 구분한다
- 실패 시 재시도, 우회, 사람 승인 요청을 구분한다
- 과도한 루프를 막기 위해 "언제 멈추고 인간에게 넘길지" 규칙을 둔다 — 예시 임계치(출발점, 실제
  값은 예산·리스크 허용도에 맞게 조정):
  - 동일 전략(또는 동일 아이디어의 변형)이 시니어 리서치에서 **3회 연속 기각**되면 자동 재시도를
    멈추고 CIO에게 에스컬레이션한다 (더 다듬어서 될 문제가 아닐 가능성이 높음).
  - 이번 사이클의 **토큰/비용 예산 80% 소진** 시점에 자동 실행을 일시 정지하고, 남은 20%를
    어디에 쓸지 사람이 우선순위를 재확인한다.
  - 같은 원인의 데이터 오류나 파이프라인 실패가 **5회 반복**되면 자동 재시도를 멈추고 G0로
    되돌려 엔지니어링이 직접 원인을 조사하게 한다 (같은 자동 재시도를 무한 반복하지 않는다).

### 작업 유형별 기본 정책

아래는 출발점 템플릿이다. 실제 값(우선순위/재시도 횟수)은 예산과 승인 정책에 맞게 조정한다.

| 작업 유형 | 빈도 | 우선순위 | 실패 시 정책 | 사람 승인 |
|---|---|---|---|---|
| 데이터 수집/검증 | 상시(스케줄) | 높음 (하류 전체 차단) | 자동 재시도 N회 → 실패 시 즉시 사람 알림 | G0에서만, 이상 탐지 시 |
| 팩터 계산 | 배치(일/주) | 중간 | 자동 재시도 → 반복 실패 시 스킵하고 로그 | 불필요 |
| 백테스트/전략 검토 | 요청 시 | 중간~높음 (채택 여부 결정) | 실패 시 사람에게 보고, 자동 재시도 지양(비용 큼) | G1 필수 |
| 리밸런싱 실행 | 정기(주기 고정) | 높음 | 실패 시 즉시 중단 + 사람 알림 (자동 우회 금지) | G2/G3 필수 |
| 리스크 점검/스트레스 테스트 | 상시~일 단위 | 높음 | 임계 초과 시 자동 알림, 완화는 사람 판단 | G2 |
| attribution/성과 보고 | 정기(주/월) | 낮음~중간 | 실패해도 운용 차단하지 않음, 재시도 후 보류 | 불필요 |
| 문서화/의사결정 로그 | 각 게이트 통과 시 | 낮음 (누적 가치) | 실패해도 별도 재시도, 운용 흐름 차단 안 함 | 불필요 |

원칙: **비가역적이거나 자본에 직접 영향을 주는 작업(리밸런싱, 리스크 한도 변경)은 자동 재시도나
우회로 실패를 덮지 않는다** — 반드시 사람에게 알리고 멈춘다. 반면 반복적이고 되돌리기 쉬운 작업
(팩터 계산, 데이터 갱신)은 자동 재시도 후 로그만 남기고 넘어가도 된다.

토큰을 계속 결제하면서 운영할 때는 특히 다음을 주의한다.

- 무조건 많이 돌리는 것보다, 결과 가치가 큰 작업에 우선 배분한다
- 같은 질문을 여러 에이전트가 반복 검증하지 않도록 작업 분담을 명확히 한다
- 연구/백테스트/운용/리스크는 각자 역할이 다르니, 중복 계산을 줄인다
- 자동화 범위를 넓히되, 비가역적 결정은 사람 승인 게이트를 남긴다
- 위 표의 "실패 시 정책"과 오케스트레이션 순서의 승인 게이트(G0~G3)를 반드시 짝지어 설계한다 —
  게이트에 걸리는 작업(백테스트 채택, 리밸런싱, 리스크 승인)에 자동 재시도만 걸어두면
  사람 승인 없이 다음 단계로 새는 구멍이 생긴다

## 결정론적 연산 엔진 및 실행 스크립트 (scripts/)

에이전트는 감상이나 텍스트 직관으로 트레이딩 결정을 내리지 않는다. 반드시 scripts/ 내의 결정론적 계산 엔진 도구를 호출하여 검증된 수치에 근거해 게이트를 통과해야 한다:

1. **CTO 데이터 피드 & G0 검증 (scripts/data_feed.py)**:
   - yfinance 기반 시장 데이터 수집 및 DuckDB 로컬 시계열 데이터베이스 자동 영속화.
   - 결측률, 0/음수 가격 이상치, 거래정지/유동성 고갈 체크 및 룩어헤드 방지.
   `ash
   python scripts/data_feed.py --tickers AAPL,MSFT,NVDA,JPM,TLT --period 1y --db market_data.duckdb [--json]
   `
2. **시니어 리서치 벡터화 백테스트 & G1 검증 (scripts/backtest_engine.py)**:
   - 모멘텀(12-1), 저변동성, 단기 반전 팩터 벡터화 연산 및 Z-Score 블렌딩.
   - 슬리피지/거래비용(10bps 기본값) 차감 후 Net Sharpe, t-stat, MDD, 연환산 회전율 산출.
   - 과적합(Sharpe > 3.5), 통계적 유의성 미달(t-stat < 1.8), 과도한 회전율(>600%) 시 G1 즉시 기각.
   `ash
   python scripts/backtest_engine.py --fee_bps 10.0 [--json]
   `
3. **CRO 2단계 리스크 평가 (scripts/risk_engine.py)**:
   - **Tier 1 (PM 데스크 개별 승인)**: Quant PM, Macro PM별 단일 자산 비중(25% 이하), 시장 중립성 체크.
   - **Tier 2 (Firm-wide 통합 노출 점검)**: 펀드 전체 자산 합산 후 섹터 노출 상한(35%) 및 **금리 민감도 쏠림(충돌 감지)** 이중 검증.
   `ash
   python scripts/risk_engine.py [--json]
   `
4. **전체 파이프라인 통합 오케스트레이터 (scripts/run_hedge_fund.py)**:
   - G0(데이터) -> G1(리서치) -> PM 할당 -> G2(이중 리스크) -> G3(CIO 배분) 전 프로세스를 자율 실행.
   `ash
   python scripts/run_hedge_fund.py --tickers AAPL,MSFT,NVDA,JPM,TLT,AMZN,GOOGL --period 1y [--json]
   `

## 출력 아티팩트

이 스킬로 설계할 때는 아래 아티팩트를 함께 정리하면 좋다.

- **에이전트 조직도 / 오케스트레이션 다이어그램**: 1~3단계에서 확정한 시작 모듈 범위에 맞춰,
  어떤 역할(에이전트)이 어떤 순서로 연결되고 G0~G3 게이트가 어디에 걸리는지, 그리고 각 게이트의
  되돌림 경로(어디로 반려되는지)까지 한 장으로 보여주는 다이어그램. 이 스킬의 가장 핵심적인
  산출물이므로 텍스트 아티팩트보다 먼저 만든다 — 다른 아티팩트들은 이 다이어그램의 각 노드를
  구체화한 결과물이다.
- **데이터 인벤토리**: 소스/주기/시점/식별자/제약/이슈
- **팩터 라이브러리**: 정의/계산법/룩백 기간/재현성/예상 편향
- **전략 카드**: 가설/신호/백테스트 요약/비용/리스크/한계/채택 여부
- **포트폴리오 규칙**: 제약/비중/리밸런싱/실행 방식
- **리스크 규칙**: 중립화/한도/스트레스/귀속 방식
- **운용 레코드와 귀속 결과**
- **의사결정 로그**: 채택/기각/수정/승인/보류 사유

## 주의 (Guardrails)

- **이 스킬의 산출물은 리서치·설계 아티팩트다.** 실거래 승인, 투자자문, 실제 자본 운용 권한을
  대체하지 않는다. 실제 매매 실행이나 자금 배분 결정은 항상 사람의 명시적 승인을 거쳐야 한다.
- 백테스트 성과가 좋아 보여도 데이터 누수, 생존편의, 룩어헤드, 이벤트 처리 오류가 있으면 무효화된다.
- 거래비용·슬리피지·공매도 비용·유동성·시장충격을 반영하지 않으면 실전 성과가 크게 달라질 수 있다.
- LLM 기반 신호는 해석의 질과 데이터 품질에 크게 의존하므로, 단독 증거처럼 쓰지 말고 보조 신호로 다룬다.
- 리스크 중립화는 "위험을 없애는 것"이 아니라 "의도한 노출을 제외한 위험을 관리하는 것"으로 이해한다.
- 비가역적 운용 행동은 자동 실행보다 승인 게이트를 우선한다.
- 데이터가 끊기거나 오류가 있을 때는, 투자 판단에 들어가기 전에 엔지니어링 검증을 먼저 한다.

## 사용 방법

- 이 스킬은 특정 코드를 대신 실행하는 스킬이라기보다, AI 헤지펀드 조직을 설계하고 모듈 간
  연결을 정리하는 **설계/운영 가이드**로 쓴다.
- 실제 구현 시에는 데이터 범위, API/파일 형식, 계산 자원, 비용 한도, 승인 규칙부터 먼저
  정의한 뒤 에이전트 역할을 붙인다 ("트리거되면 가장 먼저 할 일" 참고).
- 처음에는 작은 모듈(예: 데이터 검증 + 팩터 계산 + 단순 백테스트 + 리스크 중립화)부터
  연결하고, 이후 차익거래/매크로/귀속/의사결정을 단계적으로 확장한다.
