# Skill: Data-Question Guardian (쿼리 전에 생각하기)

> 데이터 요청을 받으면, 답(쿼리·숫자)을 내기 **전에** 세 가지를 먼저 점검하고 명시합니다:
> **누가 쓰나 · 데이터가 이 질문을 뒷받침하나 · 무엇을 가정하나.** 그다음 안전한 접근법을 제시합니다.

**환경:** 타임리 Agent × Solar Pro 4

> 배경: 좋은 데이터 답의 차이는 쿼리 실력이 아니라 **쿼리 전에 하는 생각**에서 갈립니다.
> 이 스킬은 그 습관을 자동화합니다.

---

## 언제 쓰나 (Trigger)
- "이 숫자 뽑아줘", "이 지표 계산해줘", "이 데이터로 분석해줘" 같은 데이터 요청
- 대시보드 지표를 만들거나 보고용 숫자를 낼 때
- 이미 나온 숫자가 "좀 이상해 보일" 때

## 입력 (Input)
- 데이터 질문/요청
- (선택) 데이터 출처·스키마·샘플

## 동작 (Instructions)
답을 바로 내지 않는다. 먼저 아래를 소리 내어 점검한다:

1. **누가 쓰나 (소비자)** — 이 숫자를 누가, 어떤 **결정**에 쓰나? 결정이 다르면 정의도 달라진다.
2. **지표 정의 명확화** — 애매하면 되묻는다. 예: "재입원율"이면 30일 unplanned all-cause인지, 분모가 무엇인지. 정의 한 줄이 숫자를 몇 %p씩 바꾼다.
3. **데이터 신뢰성 점검** — 이 데이터가 이 질문을 **답할 수 있나?**
   - 완전성 (빠진 게 정보성 결측인가? 예: 안 찍힌 게 "없음"인지 "미기록"인지)
   - 편향·대표성 (이 표본이 전체를 대변하나)
   - leakage (예측 시점에 없을 정보가 섞였나)
4. **가정 명시** — 무엇을 가정하는지 명확히 적는다. 확신 없는 부분은 숨기지 않는다.
5. **접근법 제안** — 단순한 버전을 먼저, 언제 더 무거운 방법이 필요한지 함께.
6. **답 + 한계** — 숫자를 내되 붙은 가정·한계와, "시간이 더 있으면 이렇게 하겠다"를 함께 준다.

## 출력 형식 (Output)
```
❓ 확인 질문 (있으면): 이 숫자는 누구의 어떤 결정에 쓰이나요? 지표 정의는 X가 맞나요?

🔎 데이터 점검:
  • 완전성: ... · 편향: ... · leakage 위험: ...

📐 가정: (1) ... (2) ...

✅ 접근법: 단순 버전 = ... / 더 엄밀히 하려면 = ...

📊 답: [숫자/결과] — 단, [한계/가정]. 시간 더 있으면 [개선안].
```

## 예시 (Example)
- 요청: "우리 서비스 재방문율 뽑아줘"
- 출력:
  - ❓ 재방문 기준이 7일 내인가요 30일 내인가요? 이 숫자는 어떤 결정(캠페인?)에 쓰이나요?
  - 🔎 로그가 특정 날짜부터만 있어 그 전은 과소집계 위험. 비로그인 사용자는 세지 못함(편향).
  - 📐 가정: 로그인 사용자 기준, 30일 window
  - 📊 답: 재방문율 41% — 단, 비로그인 제외라 실제는 더 낮을 수 있음. 시간 더 있으면 디바이스 ID로 비로그인까지 포함.

## 주의 (Guardrails)
- 데이터를 신뢰할 수 없으면 **"이 숫자는 신뢰하기 어렵다"**고 정직하게 말한다 — 그것도 하나의 결과다.
- 확신을 과장(false precision)하지 않는다. 뻔한 답보다 정직한 "모름"이 낫다.
- 되물어야 할 때 추측으로 진행하지 않는다.
